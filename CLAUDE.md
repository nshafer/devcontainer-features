# CLAUDE.md

Notes for an agent that works in this repository. The user-facing docs are the main
[README.md](README.md) and each `src/<feature>/README.md`. This file holds what those docs must not
say: approaches that failed, version history, and the reasons behind a design that a reader does
not need.

## What this repository is

Six dev container features, published to `ghcr.io/nshafer/devcontainer-features/<id>`. Each one is
a folder in `src/`, with `devcontainer-feature.json`, an `install.sh`, and the scripts that its
lifecycle hooks name. Each feature has its tests in `test/<feature>/`.

## Documentation rules

- **`NOTES.md` is the source. The generator writes `src/<feature>/README.md`.** The release
  workflow runs `devcontainers/action` with `generate-docs: true`. It rebuilds each README from
  `devcontainer-feature.json` plus `NOTES.md`, then commits the result. Never edit a feature README
  by hand. Edit `NOTES.md`, and the option descriptions in the JSON file.
- **The generator uses a JavaScript `String.replace`, so a dollar sign is dangerous.** A dollar
  sign directly before a backtick, a single quote, an ampersand or a digit is a replacement
  pattern, not text. A dollar sign before a backtick repeats the whole top of the README in the
  middle of the file. Write a code span with spaces inside the backticks, or use words.
- **All prose obeys ASD-STE100.** Lint before commit:

  ```bash
  python3 ~/.claude/plugins/cache/nshafer/asd-ste100/*/scripts/ste-lint.py --fail-over 1.5 \
      README.md CLAUDE.md src/*/NOTES.md src/egress-filter/BLOCKED.md
  ```

- **Write for a developer who does not know dev containers well.** Explain a term at first use.
  Short sentences. No em dashes, no semicolons.
- **Write in the present, about the current version.** No "version 1 did X", no "this used to", no
  upgrade notes. That history belongs in this file.
- Each feature README covers, in this order: what it does, how to install it, the options, how it
  works, what it does not do, and the risks.
- `src/egress-filter/BLOCKED.md` is shipped into the container and installed as a Claude skill at
  container start. It speaks to an agent that hit a 403, not to the person who set up the feature.

## Test and lint

```bash
make            # the targets
make lint       # shellcheck, bash -n, JSON parse, id check. Seconds, no containers.
make sandbox    # one feature
make test       # all features, the same matrix as CI
make quick      # all features, scenarios skipped
```

- `QUICK=1` skips scenarios, `FILTER=<name>` narrows to one scenario, `SCENARIOS_ONLY=1` skips the
  autogenerated test, `ARGS=` passes flags through.
- The Makefile calls the CLI through `npx`. A machine with VS Code installed has a `devcontainer`
  wrapper on `PATH` that appends `--workspace-folder`, and `features test` rejects that argument.
- Always pass `-i node -u node`. `claude`, `git-config` and `persist-homedir` key off the home
  directory of a non-root remote user, and the harness default (`ubuntu:focal` as root)
  exercises none of it.
- `sandbox` and `egress-filter` need `mcr.microsoft.com/devcontainers/javascript-node:20`. Their
  tests become root, and the plain `node` image has no `sudo`.
- `make setup` creates `~/.config/git` and `~/.config/egress-filter`. Two scenarios mount them, and
  a bind mount with a missing source stops the container from starting.
- `src/` gets shellcheck with no exclusions. The test scripts run with `SC2016`, `SC1091` and
  `SC2088` off, all three structural.

## The dev container of this repository

- The features come from the working tree, by path, with `.devcontainer/src` as a symlink to
  `../src`. The CLI refuses a feature path outside `.devcontainer/`. So **Rebuild Container** is
  how a change is tested, and a broken `install.sh` breaks this container. Recover with **Reopen
  Folder Locally**.
- Keep `docker-in-docker` at `:4` and `"moby": false`. Version 2 puts Debian on the legacy
  `iptables` backend with no check. That backend needs kernel modules that a host running nftables
  only never loads. Then `dockerd` stops at *"can not initialize iptables table nat"* and retries
  forever, while `egress-filter` gets the same refusal on every rule and still reports
  `firewall applied`. Version 4 chooses the backend in `docker-init.sh`, from `/proc/modules`. The
  option is `iptablesSwitchAtRuntime`, on by default. Debian trixie has no `moby-cli` package.
- `devcontainer.json` carries `securityOpt: ["no-new-privileges"]`, and the feature does not. The
  kernel gives `no_new_privs` to every child, so the inner `dockerd` carries it. So does every
  test container. `sudo` is setuid and cannot work there. That is why the `egress-filter`
  scenarios that need root (`strict`, `presets`, `pinned-dns`, `privileged`, `mounted-global`) set
  `remoteUser: root` instead of using `sudo`.
- `sudo` is gone in here, so `make`, `python3`, `shellcheck` and `iptables` are in
  `.devcontainer/Dockerfile`. `sandbox` also blocks the VS Code credential channels, so a push
  needs `gh auth login` in the container. That is what the `github-cli` feature is for.
- `tidewave` is the one feature this container leaves out. It needs a published port and an
  application to drive.

## Release

`.github/workflows/release.yaml` runs on a push to `main` that touches `src/**` or `test/**`. It
runs the full test matrix, publishes any feature whose `version` is not in the registry, and
commits the regenerated READMEs. **Bump `version` in the same commit as the change.** A docs-only
change needs no bump, because the docs job runs anyway.

## Spec limits that shape every feature

- A feature's `mounts` are static metadata. The CLI substitutes `${localEnv:*}`,
  `${localWorkspaceFolderBasename}` and `${devcontainerId}`, but not an option value, and not
  `${containerEnv:HOME}`, which passes to `docker run` and fails the container.
- **A feature's mount cannot be read-only.** The object has `source`, `target` and `type` only. The
  `docker run` path renders `--mount type=<type>,src=<source>,dst=<target>`, so an option on the
  end of a mount string reaches Docker. A Compose project renders `<source>:<target>` into an
  override file and drops it. No single value is read-only in both modes. So `git-config` and
  `egress-filter` declare no mounts, and the user declares them.
- **Nothing can mount at the home directory of the remote user**, because a feature cannot know the
  username. Each feature uses a fixed path, and reaches the home directory from `install.sh`, which
  gets `_REMOTE_USER` and `_REMOTE_USER_HOME`.
- **A mount cannot depend on an option.** So `persist-homedir` names fixed volumes.
- **`containerEnv` becomes a Dockerfile `ENV` before that feature's install step.** It cannot hold
  `${localEnv:HOME}` at all, and a proxy address there breaks `apt-get` in every later feature.
  That is why `egress-filter` cannot set the proxy block, and why `tidewave` cannot set
  `TIDEWAVE_HOST_PATH`.
- **A feature cannot open a port.** `forwardPorts`, `appPort` and `remoteEnv` are not in the
  feature schema. A feature gets `containerEnv`, `mounts`, `entrypoint`, `init`, `privileged`,
  `capAdd`, `securityOpt`, `customizations`, `installsAfter`/`dependsOn` and the five lifecycle
  hooks.
- **A lifecycle hook is a static string and gets no options.** Only `install.sh` sees an option
  value, so a feature bakes what the runtime needs into a generated file. A hook cannot be
  conditional either: `autostart: false` cannot remove the `postStartCommand`, only make the script
  exit early.
- **Entrypoints run in install order**, then the CLI execs the real command. An entrypoint runs
  before every lifecycle hook and before VS Code attaches.
- Every feature here declares `installsAfter` `common-utils`, so the user it creates exists first.

## claude

- The native installer runs with `su -l`, so the layout is what the self-updater expects.
- The install script hard-links the binary to `/usr/local/share/devcontainer/claude/claude`. One
  inode and two names, so the layer stores about 300 MB one time. `/usr/local/bin/claude` is a
  wrapper that prefers the home copy, because a persisted `/home` volume hides what the image put in `$HOME`.
- The Alpine branch (`libgcc`, `libstdc++`, `ripgrep`) comes from the upstream feature and is
  untested here.

## persist-homedir

- The volume is on `/home` and not on `/home/<user>`, because a mount target is a static string.
  Docker seeds an empty named volume from the image, so the home directory is copied in one time.
- `install.sh` makes the `~/.vscode-server` symlink at build time. The symlink is then part of the
  image, and it cannot race the server install.
- The build-time `chown` of `/var/local/vscode-server` does not hold. With the containerd image
  store, which GitHub runners use, the volume root comes out owned by root, and the remote user
  cannot install a server. So the feature also has an entrypoint that redoes the `chown` at
  container start.

## git-config

- **Measured:** if `~/.gitconfig` exists, git ignores `~/.config/git/config` completely. So the
  feature reads the XDG path only, and never asks for a mount of `~/.gitconfig`. A bind mount needs
  its source to exist, and an empty `~/.gitconfig` would turn off the whole config of an XDG setup.
- Version 1 declared the mount and carried the flag on the end of the target,
  `"target": "/mnt/git-config,readonly"`. Docker reads that as an option under `docker run` only.
  Under Compose it mounted the host folder at a path named `git-config,readonly`, read-write, and
  the feature found nothing to copy. Version 2 declares no mount.
- The copy happens at `postCreateCommand`, because mounts do not exist during the build. So it
  reruns on each create and refreshes a persisted home volume.
- `git config --remove-section` takes the comment lines inside the section with it.
- `dev.containers.gitCredentialHelperConfigLocation` defaults to `system`, so the live VS Code
  helper goes to `/etc/gitconfig`, which the copy never touches. The `global` value is the one that
  leaves a stale helper in the host config.
- VS Code also copies the file that `gpg.ssh.allowedSignersFile` names. A feature cannot, because
  that file can be anywhere and a feature mounts fixed paths.

## tidewave

- **Measured:** the CLI refuses a request whose `Origin` names a port other than its own. So the
  published port must be the same number on both sides. The upstream containers guide says the same
  in other words.
- `allowRemoteAccess` defaults on because nothing works without it. Docker forwards a published
  port to the bridge address of the container, not to its loopback. The upstream devcontainer
  snippet leaves the flag out, and the port then answers nobody.
- The install script detects the libc build. No option chooses it. The CLI binary is static and
  runs anywhere. The Bun
  runtime that the CLI downloads is the problem: the CLI picks the Bun build from its own triple,
  so a musl CLI on Debian fetches `bun-linux-x64-musl`, and the image has no loader for it
  (`not found` on the downloaded file). Detection is `ldd --version` naming musl, or the
  `/lib/ld-musl-<arch>.so.1` loader.
- **`TMPDIR` does not move the Bun download.** The string is not in the CLI binary. The CLI reports
  `cache_dir` from `POST /about`, and it is `$XDG_CACHE_HOME/tidewave` or `~/.cache/tidewave`.
  Putting `TMPDIR` beside it is a placement, not a redirection.
- `postStart`, not `entrypoint`: the CLI serves its working directory, which for a lifecycle hook is
  the workspace folder. An entrypoint runs as root from `/`.
- `POST /about` is the probe. A plain `GET` on it is a 405, so the probe does not mistake another
  program on the port for the CLI.

## sandbox

- **Sealing beats deleting.** A delete frees the path and VS Code makes a working socket again.
  That is why approaches built on `find -delete` need a loop that deletes again every 30 seconds.
- **Do not pre-empt a path.** An early version made `/tmp/.X11-unix` and `~/.gnupg` root-owned and
  read-only, so the socket could never be created. It works as a boundary and makes the container
  impossible to open: the helper of VS Code fails and the window stays on "Configuring Dev
  Container" forever, with no error and no timeout. `test/sandbox/test.sh` checks that those
  folders stay writable before it checks anything else. The entrypoint also runs
  `sandbox.sh repair`, because a folder that an older version sealed survives in a persisted home
  volume.
- **`vscode-ipc-*.sock` cannot be sealed.** The server calls `unlinkSync` on that path in
  `dispose()` with nothing around the call. A root-owned tombstone in sticky `/tmp` makes it throw
  `EPERM`, and the attach hangs. Same shape as the failure above. So `blockCodeCli` defaults to
  `false`.
- **Measured race window:** with the 1 second poll alone, 15,299 usable connections over 993 ms.
  With `inotify`, 7 connections over 5 ms. About 2,000 times better, and the reason the feature
  installs `inotify-tools`.
- **Wayland is a bind mount, not a socket in the container.** A `chmod` on it writes through to the
  host socket of your desktop session. Every mutation is gated on a `/proc/self/mountinfo` check,
  and `test/sandbox/wayland_bind_mount.sh` shows the write-through and then proves the guard.
- **Depth 3, not 2.** `XDG_RUNTIME_DIR` is `/tmp/user/<uid>`, and the git credential socket lives
  there.
- **The manifest is reported on, never acted on.** Root cannot read another user's
  `/proc/<pid>/environ` without `CAP_SYS_PTRACE`, which Docker does not grant, and a feature that
  granted it would let the remote user ptrace the daemon. Also, root must not `chmod 000` a path
  that the remote user named, because that is a denial-of-service primitive against `/etc/passwd`.
  So the unprivileged `postStart` and `postAttach` hooks read `REMOTE_CONTAINERS_SOCKETS` and warn.
- **The env scrub lives in `/etc`,** never in `$HOME`, because `persist-homedir` masks whatever the
  image wrote to `~/.bashrc`. A scrub installed there would work one time.
- **`no-new-privileges` cannot come from the feature.** The flag blocks every setuid path, `sudo`
  included, so it cannot coexist with restricted sudo mode, and feature metadata cannot be
  conditional on an option. It moved to `devcontainer.json`.
- The option name is `sudoMode` and not `sudo`, because each option becomes an `ENV` line in the
  image, and a container-wide `SUDO=drop` breaks the common `$SUDO apt-get install` pattern.
- Version history: 1.x had one `blockVscodeIpc` option for three sockets that are not equivalent.
  Version 2.0 split it into `blockCodeCli` (default false), `blockGitAskpass` and
  `blockExtensionIpc`. In
  2.x `blockGitAskpass` shipped open, so a push used the host token. 3.0 closes both credential
  channels by default. The CLI warns about an unknown option, so an old config still builds.
- Research sources for the `code` CLI channel: the container server at
  `/tmp/vscode-remote-containers-server-<uuid>.js`, the server CLI in
  `~/.vscode-server/bin/<commit>/out/server-cli.js`, and
  `src/vs/workbench/api/browser/mainThreadCLICommands.ts` on the host side. The tests ran on VS Code
  1.137.0 for the `open` behavior, and on git 2.55.0 for `core.fsmonitor`.

## egress-filter

- Version 1 declared the mount with `"target": "/mnt/egress-filter,readonly"`, with the same
  Compose failure as `git-config` version 1. Version 2 declares no mount.
- **The inner Docker daemon was a complete bypass.** `docker run alpine wget https://anywhere`
  returned the page, because the packets of a started container go through `FORWARD` and the `-m
  owner` match never sees them. `DOCKER-USER` is the chain to use: Docker promises never to rewrite
  it, and reads it before its own rules.
- **`dockerd` reads `daemon.json` one time, at start.** With `docker-in-docker` listed before
  `egress-filter`, its entrypoint runs first, the daemon comes up before the file is written, and
  every pull for the life of the container goes unproxied. The failure reads as a registry timeout.
  So `install.sh` writes the file into the image, `egress.sh` writes it again at container start,
  and then asks the running daemon with `docker info`. A restart happens only when no containers
  are running, because the restart would take them with it.
- **The profile.d file is written at build time** because VS Code starts its server seconds before
  the entrypoint runs, and the environment probe result is what the extension host keeps for the
  life of the window. Timeline measured: PID 1 at 19:05:56.0, server at 19:05:57.6, entrypoint at
  19:05:58.0, file at 19:05:58.4.
- **`/etc/environment` stays a container-start file.** A build-time copy would point a later feature
  at a proxy that does not exist yet. The CLI appends the whole container environment to that file
  after the entrypoint, and PAM takes the last assignment, so the watcher rewrites the block until
  it is last.
- **`curl` ignores an uppercase `HTTP_PROXY`** on purpose, because of the httpoxy vulnerability.
  Measured: `HTTP_PROXY` alone gives `000` for plain HTTP, `http_proxy` alone gives `403`. So the
  block carries both spellings.
- **Local subnets became allowlist patterns** so that `NO_PROXY` needs no subnet, which is what
  makes the `containerEnv` block the same on every machine. Before that, a client that read
  `HTTP_PROXY` sent a peer request to the proxy, which denied the address.
- **`upstreamProxy: auto` reads PID 1**, not this script's environment. `/etc/environment` names
  this proxy, so a second `egress.sh up` from a shell would chain the proxy to itself. The feature
  detects a self-chain and drops it.
- **Busybox `wget` does not survive a chained pair of proxies.** It cannot do TLS through a proxy,
  so it sends `GET https://host/...` instead of `CONNECT`. One proxy answers that. A parent proxy
  refuses it. Everything that sends `CONNECT` is fine.
- **Re-applying the firewall empties each chain first**, so `OUTPUT` is empty with an `ACCEPT`
  policy for about a millisecond. With an inner daemon this happens again on each
  `docker network create`.
- `egress.sh` writes the Claude skill at container start, not at build time, because
  `persist-homedir` masks `$HOME`. Skills are model-invoked, so the description names the symptoms:
  a 403, a `CONNECT tunnel failed` message, an npm error about permissions. It is deliberately
  pushy. `skill-creator` notes that
  Claude tends to under-trigger skills.
- A missing kernel module does not leave half a firewall: the chain comes down, `up` returns
  non-zero, and the container starts with open egress and says so.
- `python3` merges `daemon.json` and `~/.docker/config.json`, so registry logins and a `log-driver`
  survive. Without `python3`, and with a file that exists, the feature prints the block instead.
